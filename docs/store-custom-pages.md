# Custom store pages by search intent

This is an en-US publishing specification for three evergreen intents. It uses only the store images and app routes committed on `main` at `faf033e`. It creates no page or asset in either store. The default listing remains the broad introduction; each proposed page changes the first three screenshots and leading copy to answer one narrower search.

## Destination and publishing gates

Use `suuudokuuu://` as the Apple custom product page (CPP) deep link for all three pages. It opens the Home route, where the player can choose a difficulty, select Standard/Relaxed/Hardcore mistakes, and start a puzzle. `/game` redirects to Home when there is no current run. Home reads saved settings and does not consume URL parameters for difficulty or mistakes, so **none of these pages preselects a tier or mode**. Do not substitute `/game?difficulty=...`, `/play?difficulty=...`, or a made-up relaxed-mode link. Apple supports CPP deep links on iOS/iPadOS 18 or later; older systems may show the ordinary launch experience. The Play `listing` parameter selects a store listing, **not an in-app destination**. See [Home](../packages/app/src/screens/components/home-screen/home.screen.tsx), [game route](../packages/app/src/app/game.tsx), [scheme/package configuration](../packages/app/brand.config.js), and [Apple CPP guidance](https://developer.apple.com/app-store/custom-product-pages/).

The images below are existing framed en-US files. Apple iPhone files are under `packages/app/fastlane/screenshots/variants/dark/ios/en-US/`; Apple iPad files are in the same directory. Play files are under `packages/app/fastlane/metadata/android/en-US/images/phoneScreenshots/`. File numbers describe the current default order; upload in the order listed for a custom page. Retain the remaining default images and metadata unless this table specifies a change. Reuse requires checking that each asset is accepted for the target CPP and device slot in App Store Connect; this document does not claim an Asset Library upload. The dark set is the configured iOS default.

Apple CPP keywords are **assignments from the latest approved app version**, not a new free-text keyword field or a new 100-byte budget per page. The Apple terms below are candidate assignments drawn from the repo's en-US `keywords.txt`; confirm each is available in the live CPP keyword selector before publishing. Each term belongs to one proposed page only. If an eligible term is absent or another page already owns it, omit that assignment until the base listing is updated and approved; the page can still be reached by its unique CPP URL. Google Play search targeting likewise requires choosing actual available search terms and reviewing their spelling/translation bundles in Play Console. The Play terms are proposed targets, not a claim that traffic or eligibility has been observed. [Apple setup](https://developer.apple.com/help/app-store-connect/create-custom-product-pages/configure-multiple-product-page-versions) · [Play setup](https://support.google.com/googleplay/android-developer/answer/9867158).

## Verification and measurement

Before store submission, test the **production** iOS build on iOS 18+ by opening `suuudokuuu://` from outside the app for each proposed CPP and recording that Home visibly offers difficulty selection, Relaxed mistakes, and Start puzzle. Repeat on a production Android build to confirm the same Home route if a campaign separately links into the app. Test fresh install and a saved in-progress run; confirm no CPP silently selects a tier or replaces that run. Open each published Play URL to confirm its `listing` parameter shows the matching listing, and use each live Apple CPP URL to confirm its matching screenshot order and promotional text. The source audit above establishes route intent, **not native runtime proof**; this proof remains a release gate. Apple's generated CPP URLs and live keyword eligibility also require store access; do not invent page IDs or claim a live configuration.

For each internal page name, record publication date, selected keywords, CPP URL or Play `listing` value, and screenshot order. Compare the page with the default listing over the same storefront, device type, and date window. On Apple, use App Analytics Acquisition for page impressions → downloads/redownloads → conversion rate, then retention where available. On Play, record store listing visits and unique Install clicks separately from CTR, which counts visitors who click Install, Open, or Pre-register. Track acquired and retained installers separately where available, because Play's current listing report emphasizes clicks. Segment organic keyword traffic from visits to a shared URL; a `listing` value is a page identifier, not proof of campaign attribution. Keep the comparison descriptive until traffic and attribution are sufficient; no A/B test or paid campaign is part of this issue. [Apple analytics](https://developer.apple.com/app-store/custom-product-pages/) · [Play listing metrics](https://support.google.com/googleplay/android-developer/answer/9859173).
